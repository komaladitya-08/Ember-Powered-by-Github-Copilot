# Apple design and testing research for Ember

Research date: 4 November 2026. Primary sources: Apple Human Interface Guidelines (HIG), Apple Accessibility documentation, and Xcode testing documentation. Source pages were fetched online, including Apple's official Markdown versions, and cached in `research/apple-sources/`.

Scope context supplied by the main reviewer: Ember is an Electron desktop companion for macOS 13+, Windows 10/11, and RHEL8, with Home, quick Ask, companion/overlay bubbles, action approvals, voice, command, and remote desktop windows. The recommendations below are an interpretation for that product, **not findings that these defects exist in Ember**. Apple HIG recommendations are design guidance, not universal App Store rejection rules. macOS dimensions must not be replaced by iOS conventions.

## Highest value Apple principles for this product

| Area | Apple evidence | Application to Ember (review proposal) |
| --- | --- | --- |
| Control and reversibility | Generative AI guidance calls for clear AI disclosure, people retaining control, dismiss/retry/revert, and nearby refinement controls. Its June 2026 update adds refinement and meaningful generation feedback. | Provide a consistent Stop, Retry, Edit, and result feedback model across Home, Ask, and task surfaces. Make canceled, failed, and complete states distinct. Review resulting changes before significant actions. [Generative AI](https://developer.apple.com/design/human-interface-guidelines/generative-ai) |
| Generation status | Apple recommends specific, truthful feedback during generation, plain-language errors and a next step. Progress should live in a consistent location; use determinate progress only when it can be measured. | Show what is actually happening, such as connecting, searching, waiting for approval, or writing a response. Avoid fabricated percentage or pretend reasoning. Preserve a task trail when collapsing to a bubble. [Generative AI](https://developer.apple.com/design/human-interface-guidelines/generative-ai), [Progress indicators](https://developer.apple.com/design/human-interface-guidelines/progress-indicators) |
| Focus and interruption | Apple says to avoid changing focus without user interaction. macOS distinguishes main, key, and inactive windows; custom windows must preserve understandable differences. | Passive bubbles should not capture typing from another app; an invoked Ask field should. Dismissal should restore the previous focus target. Test each keyboard and programmatic window transition. [Focus and selection](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection), [Windows](https://developer.apple.com/design/human-interface-guidelines/windows) |
| Window restraint | New windows can preserve context, but excessive default window opening creates clutter. macOS should allow move, resize, hide, show, and familiar multitasking. | Assign a clear role to companion, Ask, Home, approvals, and remote desk. Offer a path from short interaction to durable task detail without duplicate competing windows. Avoid multiple stacked approval dialogs. [Windows](https://developer.apple.com/design/human-interface-guidelines/windows), [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos) |
| Modality | Modal views require a clear benefit, a short bounded task, an obvious dismissal, and protection against losing authored content. Avoid app-within-app modal hierarchies. | Use a focused approval for a concrete consequential action; keep routine status and task history nonmodal. Allow dismissal without accidentally approving and retain the draft/task context. [Modality](https://developer.apple.com/design/human-interface-guidelines/modality) |
| Material hierarchy | Liquid Glass is for controls/navigation above content; Apple explicitly discourages it in the content layer and warns against overuse. Standard materials differentiate content. | Prefer a quiet solid or standard-material transcript/work area; reserve glass for navigation or compact functional chrome. A no-blur Electron fallback should preserve hierarchy and contrast, rather than emulate glass everywhere. [Materials](https://developer.apple.com/design/human-interface-guidelines/materials) |
| Platform fit | Mac apps should support familiar menu commands, keyboard shortcuts, resizable windows, and smooth active/inactive transitions. Apple discourages custom window frames and imperfect imitations. | Treat native title bars, platform shortcuts, focus rings, close/minimize behavior, and Settings as functional UX. A cross-platform design need not clone macOS chrome on Windows or Linux. [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos), [Windows](https://developer.apple.com/design/human-interface-guidelines/windows) |
| Progressive disclosure | HIG Layout recommends clear importance order, alignment, grouping, and progressively exposing secondary choices. | Keep the prompt and the current task state prominent. Move technical configuration and seldom used controls into labeled secondary views. Use consistent mode names across all entry points. [Layout](https://developer.apple.com/design/human-interface-guidelines/layout) |
| Input | Apple supports paste/drag and drop, appropriate clear prompts, choices when simpler than typing, and timely validation. Standard keyboard commands should retain their meanings. | Support multiline composition, text selection, paste, attachments where actually supported, and recoverable validation. Explain Send/newline shortcuts, and avoid firing a send while IME text is being composed. IME detail is a review proposal, not a quoted HIG rule. [Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data), [Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards) |
| Privacy and permissions | Ask for protected resources when the feature actually needs them; disclose what is collected, shared, stored, or used for training. AI guidance recommends minimizing remote data. | Explain current screen/context capture, microphone state, provider processing, retention and control. Request microphone/screen access at use, and provide a useful denied/unavailable state. Inspectability and a local stop control matter more than a one-time disclaimer. [Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy), [Generative AI](https://developer.apple.com/design/human-interface-guidelines/generative-ai) |
| Feedback | Apple recommends feedback proportional to significance, accessible in multiple ways, and near its affected item. Reserve alerts for critical/actionable matters. | A copied state can be inline; a generation error should be associated with that turn/task and preserve retry context. Audio must not be the sole way to notice voice/task status. [Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) |
| Background activity | Foreground notifications should be discoverable and unobtrusive. Repeated notifications for the same event and sensitive notification content are discouraged. | Quiet completion badges or task status are preferable to repeated bubbles, sounds, and focus changes. Let people mute/passively show the companion, and avoid exposing full prompts over another app. [Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications) |

## Accessibility measures: correct macOS interpretation

Apple's current accessibility table lists **macOS default text 13 pt and minimum 10 pt**, and **default control size 28×28 pt, minimum 20×20 pt**. These are platform recommendations; 10 pt is a lower boundary, not a sensible default for a long chat transcript. Use comfortable body text, strong hierarchy, sufficient spacing, and adjustable reading size. Apple's target is ideally at least 200% enlargement, through custom UI or platform text scaling. CSS pixels and Apple points should not be declared identical without checking Electron zoom and display scaling. [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

For a practical product target, aim for at least **4.5:1 contrast for normal text** and **3:1 for large text/non-text controls where applicable**, checking real composited backgrounds. Apple recommends contrast calculators, semantic colors, testing both appearances, not relying on color alone, keyboard-only support, simple gestures plus alternatives, accessible labels, and reduced excessive motion. The exact web WCAG interpretation should use WCAG definitions rather than treating Apple’s simplified point-size table as a web specification. [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

For a no-GPU cross-platform app, system Reduce Transparency, Increase Contrast, Reduce Motion, keyboard focus, and text scaling need explicit verification; CSS styling does not establish that native settings are observed. Apple’s Liquid Glass advice does not require adding blur to macOS 13–15 or Linux. Treat fallback legibility, rendering cost, and predictable behavior as release criteria. This compatibility recommendation is an Ember-specific interpretation of [Materials](https://developer.apple.com/design/human-interface-guidelines/materials) and [Testing system accessibility features](https://developer.apple.com/documentation/accessibility/testing-system-accessibility-features-in-your-app).

## Apple-based testing plan adapted to Electron

Apple's sequence is: inventory the tasks on every screen; build a matrix of supported devices/settings/assistive technologies; execute the tasks with each; diagnose and fix; repeat. An automated accessibility audit alone does not guarantee accessibility. [Performing accessibility testing](https://developer.apple.com/documentation/accessibility/performing-accessibility-testing-for-your-app), [Performing accessibility audits](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app)

| Test group | Concrete Ember scenarios | Pass evidence |
| --- | --- | --- |
| End-to-end core tasks | Fresh launch → configure provider → Ask → submit → read → follow up; open Home; find past task; stop; retry; approve/reject; voice start/stop; reconnect. | A user can finish each task and understand its current state. Store exact version, OS, screen/scale, steps, result and screenshots. |
| Keyboard only | Invoke Ask globally, compose multiline, traverse controls, open menu, cancel, switch windows, move focus to history/detail, close, restore origin. | Logical Tab/Shift-Tab order, visible focus, no keyboard trap, shortcuts discoverable, no conflict with OS commands; passive status never steals keystrokes. |
| macOS assistive technology | Run the same tasks with VoiceOver, Voice Control, Full Keyboard Access, and Switch Control; include overlay windows and approval buttons. | Correct names/roles/states and reading order; task completion possible without sight or pointer; no token-by-token speech flood while streaming. The streaming rule is a proposed chat acceptance criterion. |
| Text and display | Smallest supported window; 200% app text/zoom; long labels, long responses, localized strings, RTL; Retina/non-Retina/mixed-DPI displays. | No unreadable clipping, overlapping, inaccessible buttons, or lost draft; transcript and code remain readable/scrollable. |
| Appearance and preferences | Light/dark, Increase Contrast, Reduce Transparency, Reduce Motion, Differentiate Without Color; busy/bright/dark desktop behind overlays. | Contrast measured in real states; status identifiable by text/icon as well as color; steady readable content; unnecessary animation ceases. |
| Window lifecycle | Open Ask during typing elsewhere; incoming completion/approval while another app is active; Cmd-Tab, Dock activation, close/reopen, sleep/wake, monitor removal, display scaling changes. | Correct key/main/inactive state, no offscreen or inaccessible windows, no prompt loss, no unintended focus transfer, predictable placement. |
| Permission paths | Microphone and screen capture allowed, denied, revoked, restricted, unavailable; offline/provider unavailable; reconnect. | Just-in-time explanation, useful fallback, recovery path, no repeated permission nagging, accurate capture state. |
| Generation robustness | Fast reply, slow first token, stalled stream, interrupted network, repeated Send, cancel while tool runs, expired approval, canceled/retried action. | Truthful status and specific recoverable error, preserved authored input, no duplicated side effect, action state reconciled after restart. |
| AI outcome evaluation | Ambiguous, out-of-scope, poorly phrased, sensitive and diverse requests; known factual tasks; updated models. | Clear limitations and safe scope, useful corrective guidance, users can inspect/correct/retry/report outputs; retest after model changes. |
| Performance | Cold/warm global invocation, long transcript, streaming, overlay movement, remote desk, idle companion; no-GPU supported hardware. | Record time to visible response, input latency, frame stability, CPU/memory and idle cost. Set Ember-specific budgets from baseline; Apple does not supply a universal chat latency threshold. |

For native macOS verification, Accessibility Inspector checks labels, hit regions, contrast, inaccessible children, hierarchy integrity and actions; audit **every screen/state** and export the HTML report. `XCUIApplication.performAccessibilityAudit` can automate current-screen checks where the test environment supports them. Verify tool applicability to the packaged Electron build instead of promising that Xcode tests are already wired up. [Performing accessibility audits](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app)

Use the existing Electron browser/E2E stack for DOM interactions and visual states; add real macOS accessibility and window tests to cover behavior a browser preview cannot establish. This is a proposed implementation strategy. Apple recommends a pyramid of fast logic tests, integration tests and fewer task-oriented UI tests plus targeted performance coverage; Apple tooling uses XCTest with XCUIAutomation for UI tests, not Swift Testing alone. [Xcode testing](https://developer.apple.com/documentation/xcode/testing), [XCUIAutomation](https://developer.apple.com/documentation/xcuiautomation)

## Proposed release gates (Ember recommendations, not Apple mandates)

1. Every shipped surface and its idle, working, failure and empty states has been reviewed on the supported desktop platforms.
2. A keyboard-only and VoiceOver user can complete core Ask, Stop, Retry, approval and Settings flows.
3. No passive companion event steals input; explicit global invocation focuses correctly and dismissal returns context.
4. Normal text meets the agreed contrast target in both themes and the opaque fallback, with 200% text/zoom usable.
5. Losing connectivity, permissions or a provider preserves drafts and yields an understandable next step.
6. UI state cannot misleadingly show an operation as canceled, approved or complete while a different action state persists.
7. No critical accessibility audit result is waived without a documented rationale and manual verification.
8. Compare usability on actual packaged releases; a static preview is not evidence for system capture, native focus, permissions or performance.
