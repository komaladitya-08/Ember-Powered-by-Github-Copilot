# Experimental Windows coding files

This native file foundation now backs the draft Windows files-only product adapter through
[Windows project resources](EXPERIMENTAL-WINDOWS-PROJECT-RESOURCES.md). Copied editing, sealed review,
continuation, export and Forget have separate native and genuine Electron evidence. This module supplies no
command runner or Windows sandbox, and does not resolve the LPAC child/PowerShell compatibility failures.

`WindowsCodingCopy.create({ source, privateBase, protectedPaths, signal, current, limits })` captures a host-selected source directory into a fresh private NTFS directory. `WindowsScopedCodingFiles.create({ copy, signal, current, workspace, limits })` exposes structural `/work` list, full-text read, literal search, create/replace, mkdir, and delete operations. Results contain virtual paths and fixed errors. Native handle tokens and host paths stay in the trusted host.

The native module opens one path component relative to a pinned directory with `NtCreateFile`, `OBJ_DONT_REPARSE`, and reparse-point handling. The initial selection accepts fixed local NTFS drive paths; network paths, device paths, mount/junction/symlink traversal, alternate data streams, ambiguous portable names, special files, and multi-link files fail closed. Source and storage-ancestor handles remain open without delete sharing. Source file handles allow neither shared writes nor deletes for the capture interval, and enumeration IDs, metadata, complete content reads, and final receipts must agree. Source handles receive no write/delete access. Source directories are never modified or granted new ACLs.

Persistent private-copy directory handles retain the exact object with read/query and add-child rights, omit `DELETE`, and allow delete sharing. They pin identity rather than forbid namespace changes. Lease checks still compare canonical path and file identity before and after asynchronous work; the native regression replaces a relocated private root's pathname and requires rejection before the tool callback can touch either tree. Fresh-directory creation first holds a short-lived `DELETE` creation handle for rollback, then verifies a separate non-`DELETE` handle opened by NTFS file ID before closing the creation handle. Each copy-directory lease captures an immutable parent lifetime token and validated single component; transfer preserves those fields. Directory deletion opens that component with `DELETE`/query/traverse access relative to its still-held parent using the existing no-reparse `NtCreateFile` options. The parent must be the live original base for a root or a live copy directory in the same root for a child. Full current parent, original, and candidate receipts and private ACLs must agree before immediate disposition; a missing parent or mismatched candidate rejects without an absolute-path/by-ID deletion fallback. The original identity pin stays held, and candidate close is independent and terminal on uncertainty. Source/base pins and the bootstrap are unchanged; no host ACL or capability grant is added.

Existing private-copy file handles retain `READ|DELETE` access and now share `READ|DELETE` (`5`), with shared writes still denied. Source file handles keep read-only sharing (`1`), and fresh temporary write handles keep read/write sharing (`3`). The exact old target handle stays held through replacement. Full-content tool guards and their one-link requirement are unchanged; the native test probes the displaced raw handle's OS readability without exposing an unlinked object through ordinary text tools.

The source cannot overlap the private base or protected roots, checked through canonical volume-GUID paths. Fresh private storage may live beneath Ember's protected app-data parent; only new protected child objects are written there, and the parent never becomes a tool source. Fresh destination objects have protected owner/SYSTEM DACLs, fresh file IDs, one link, and bounded sizes. Their exact native identities and DACLs are audited again for each lease. Hidden/system source entries fail capture so a fresh object cannot erase a source privacy marker. Credential paths and complete decoded file contents pass the shared asynchronous privacy guard before capture; read ranges and searches scan complete text before returning any part. Known binary files remain unavailable to text tools. An opaque privacy generation is captured before source awaits and checked again around asynchronous work, so global Forget permanently revokes the old copy, including metadata leases.

Every broker operation holds both the copy's serialized lease and the caller-supplied `workspace.files` lease. A future command backend must supply a lease that proves all its command writers have stopped. The copy alone cannot provide that process proof. Lease contexts expire when their callback settles. Stop revokes admissions synchronously and drains pending file work. Writes create and verify a fresh temporary file, then request handle-relative atomic rename; there is no awaited work between the final authority check and mutation. The initial atomic replacement failures and their verified correction are recorded below. Cleanup deletes only audited private objects by their exact held handles. An uncertain native handle close is a typed terminal error, retains failure, and blocks this experimental boundary until process restart.

Unrelated same-user or administrator processes on the host are outside this boundary. This does not claim a transaction against such processes, protection from a compromised trusted host or directory-fsync crash durability. The separate file-only resource owner supplies publication and cleanup/export authority. Fresh copies do not grant an LPAC package SID; a future command backend must separately verify process isolation, writer quiescence, fresh-workspace package access and revocation before broker admission.

The dedicated `experimental-windows-files.yml` workflow runs real native tests on Windows Server 2022 and 2025 independently of the LPAC command runtime. Cases cover real hardlinks, junctions, protected canaries, source replacement, writable source handles, atomic overwrite with an open target, expired handles/leases, full-text secrets, Stop, privacy-generation retirement, bounds, and ACL/hidden-attribute tampering. It skips only on non-Windows hosts; configured Windows failures remain failures.

## Explicit files-only workspace adapter (16 November 2026)

`WindowsFileOnlyWorkspace` connects the copy, one file broker and the sealed artifact producer to the common
`CodingReviewWorkspace` lifecycle. This interface has no command or Node capability. The worker calls its host-only
seal only after awaited SDK/controller and file-broker closure; uncertain startup or closure suppresses review
publication. The adapter also drains its own broker and ordinary copy leases before attesting that seal.

The adapter retains the exact producer output and original source capability before awaiting copy removal. Only
verified copy removal yields `cleanup: "complete"`. The resources owner records both capabilities and transfers the
exact result synchronously before awaiting registry publication. Close reclaims only untransferred results. A close
waiting for an export permits that immediate transfer; once artifact disposal starts, transfer is permanently
refused. Failure retains the owned receipt and cached cleanup barrier. Closed copies and transferred adapters drop
their cached private review references.

A registry may claim an artifact and then reject publication. The Windows store records a weak acknowledgement only
after every native deletion and handle close succeeds, allowing the producer to settle cleanup for that exact token
and directory. It never probes or removes a later object at that name, accepts no forged token, revives no claim, and
does not bypass a terminal native cleanup failure.

Portable ownership/race tests and new native adapter cases cover these seams. The earlier sealed-copy head
`86d2fc43` passed 53 units, 29 artifact cases and 21 native sealed-review cases per server in run `43804441087` on
Server 2022 and 2025. Subsequent resource/product head `60ec77d1` passed 410 artifact/review/resource checks and
204 controller/Electron/ZIP checks across both servers, without skips; see the linked project-resource evidence and
[acceptance record](WINDOWS-CONDUCTOR-ACCEPTANCE.md). Physical Windows clients and live providers still require
acceptance. Commands and dependency installation remain unavailable.
