# Ember product experience review

4 November 2026. Review baseline is main after the reliability work in #164. The expected load is one person at a desktop, with the listener running locally when enabled, up to two tasks and two guides, and a retained memory graph of up to 5,000 facts. This review follows first run, a spoken request and its answer, approval and Stop, task activity, model and tool setup, and the data and processes those paths use. [Earlier review and acceptance gaps](review-2026-11-03.md)

## Product direction

Voice should be the easiest way to start and stay in a conversation. Ember needs a clear listening state, a way to start listening after a missed wake, a way to see or correct what it heard, and a reliable way to stop playback and tasks. The same requests and safety controls need a keyboard path. Replies should say the useful part first, with longer material and artefacts available on screen.

Copilot capabilities should appear where people need them. Conversation settings can explain the selected model, context and usage. A separate project workspace can explain its files, permissions, changes and history. General desktop tasks continue through Ember's own tool and confirmation policy.

## Findings and work order

Sign-in progress loses actionable errors and warnings on render. | Keep failed and partial saves on the form, retain edits made during saves, and make completion follow the current step. | 3 | A streamed link or code span can reach speech half formed. A system utterance behind a long answer can time out before it reaches the speaker. | 4 | A failed speech correction leaves a dead form, and Forget by list index can delete the wrong correction after a concurrent update. | Retain the editable correction on failure. Bind removal to the exact saved entry and test stale clicks and replacement entries. |
| 5 | Voice control depends on wake detection even when the user is at the keyboard. The model process can become ready before the microphone capture is ready. | Add a keyboard-accessible **Listen once** action that reports permission, model and capture readiness. | 7 | Playback scheduling shows that audio was queued, and gives a coarse completion signal. It cannot account for the words someone heard before interruption. | Record local request-to-first-audio and interruption-to-silence measurements. | 8 | The app has model choice and aggregate session usage but hides the conversation window reported by Copilot. | 9 | The runtime normalises dotted MCP tool names. A grant keyed by a display name alone can be ambiguous when a tool shares that runtime name. | Map raw names to the runtime name, reject ambiguous grants, and verify the originating server and tool metadata. | 10 | Upkeep of the retained memory graph blocked the main process for 1.27 s at 1,000 synthetic same-subject facts and 36.3 s at 5,000. | Reuse term sets, yield during upkeep, and discard a pass when the live graph changes or consent ends. ## Project work

In Home under Copilot, **Project work** can review selected source files, plan changes, or draft a patch for inspection. It shows the selected filenames before sending. The connected model receives the request and the selected UTF-8 text, up to six files and 64 KiB combined. Ember blocks recognised credentials and keeps a project request separate from the conversation, with no tools or workspace access. The answer is available in Home for inspection and copying. The temporary Copilot session is deleted after the request and cleaned up on the next connection if a crash interrupted it. Applying patches, running commands and resuming project sessions are separate capabilities.

## Release evidence

For each PR, keep the regression, the affected native smoke run and the exact GitHub head together. For speech quality, report wake misses and false wakes, endpoint truncation, request-to-first-audio, quiet-after-Stop, and correction harm separately. The existing targets are wake-to-earcon under 300 ms, first action p50 under 3 s and p95 under 6 s, fewer than 5% missed wakes, fewer than 0.5 false wakes an hour, and Stop within 300 ms.

Automated tests use synthetic audio. Hands-on acceptance covers built-in and external microphones, speakers and headphones, accents and noise, enrolment and unknown voices, mute, lock and device recovery, keyboard-only work, and the platform screen readers. Report the model, backend and sample counts. Compare audible timing with the app's local events using an authorised test signal. ## Voice and task controls

- **Listen once** in Ask and Home takes one request. With wake listening off, Ember starts the recogniser on demand and closes temporary microphone capture before answering. With wake listening on, it returns to listening for the wake word. It explains when listening is unavailable, and the control is then shown and announced as unavailable and takes no press. In Ask, a block that only Settings can lift (the speech models aren't downloaded) shows **Set up voice in Settings…** instead, which opens Home at Voice, and where the organisation turned voice off Ask leaves Listen once out and opens a row shorter. Speech must start within 8 s of the press; a request still being said then is heard to its end (at most 20 s from the press, where what was heard so far is sent and Ember says it only caught the first part), but only one that stands out from the room as it was before that speech began: a TV's or a colleague's talk going on as the window opened ends it at 8 s with “No request heard. Try again.”, never as the request. Speech begun in the window's first second can't be told by its loudness from such talk resuming after a pause, so it is heard to its end only within 12 s of the press; talk still going on then ends the window the same way. A request that trailed off and is held for its rest when the window ends goes as it was. While a screen reader runs, what Ember's windows announce as the window opens (its status lines, the button's new name, Settings' voice line), which the screen reader says through the speakers, is left off the start of what is heard: the request after it goes alone, and an announcement heard on its own leaves the window open for 8 s after it. Settings' voice line says “Listening…” for as long as the window is open. Pressed while Ember talks or answers, it stops that first, as “Hey Ember” does, and listens once Ember's voice has stopped (its tasks go on; a question still has to be answered first, and one that comes while it listens ends the listening, the request with it, and the control says “I stopped listening to ask you something. Answer it, then ask again.” until the question is answered). Opening Ask with its shortcut gives a keyboard route.
- **Thinking effort for tasks** uses the selected Copilot task model's advertised levels. The choice is validated as each new task starts. The default, unsupported models, and provider or policy conditions are handled by the same model settings.
- The recognition benchmark reports helped and harmed reference words separately, and includes an intentional repetition set. In one Windows run across 68 synthetic clips, the normal voice fixtures had two helped words and one harmed word after vocabulary correction. The intentional repetition set had a raw word error rate of 28.9% over 38 words. Use a held-out device corpus to choose changes to endpointing, repetition handling and recognition.

## Playback, Activity and memory follow-up

- Request transcription preserves a phrase repeated twice inside a longer request, such as “New York, New York”. The decoder comparison showed that the repeat filter had removed words the model heard correctly. Whole-segment doubles and longer decoder loops still use the repeat filter. Wake and Stop checks keep their original repeat handling.
- The local `voice.hush_ack` event measures elapsed time from a hush request to confirmation from the renderer that was speaking. It records the renderer kind and elapsed milliseconds. Real-device measurements are still needed to establish when audible output stops.
- Activity reads older audit blocks only until it has the requested recent entries. In five runs on a synthetic 104 MB monthly file with a fresh Activity cache and a warm filesystem cache, the same latest 500 entries took a median of 839 ms before the change and 6 ms after it on Windows. The WSL run went from 1,000 ms to 3 ms. Both read 256 KiB with the new reader. Files with fewer valid entries may require scanning further back.
- Memory distinguishes opposing statements during initial deduplication and later upkeep. An explicit reversal of a single-valued preference closes the previous fact through the existing history rules. Saved memory opens only after Ember verifies its GitHub owner. Older data without ownership stays hidden until the user clears it.
