# Ember product experience review

4 November 2026. Review baseline is main after the reliability work in #164. The expected load is one person at a desktop, with the listener running locally when enabled, up to two tasks and two guides, and a retained memory graph of up to 5,000 facts. This review follows first run, a spoken request and its answer, approval and Stop, task activity, model and tool setup, and the data and processes those paths use. [Earlier review and acceptance gaps](review-2026-11-03.md)

## Product direction

Voice should be the easiest way to start and stay in a conversation. Ember needs a clear listening state, a way to start listening after a missed wake, a way to see or correct what it heard, and a reliable way to stop playback and tasks. The same requests and safety controls need a keyboard path. Replies should say the useful part first, with longer material and artefacts available on screen.

Copilot capabilities should appear where people need them. Conversation settings can explain the selected model, context and usage. A separate project workspace can explain its files, permissions, changes and history. General desktop tasks continue through Ember's own tool and confirmation policy.

## Findings and work order

| Priority | Observed problem | Change and acceptance |
|---|---|---|
| 1 | First run can advance after an unsuccessful introduction save, accept duplicate consent clicks, or advance after Back. Sign-in progress loses actionable errors and warnings on render. | Keep failed and partial saves on the form, retain edits made during saves, and make completion follow the current step. Check duplicate clicks, delayed replies, successful retry and keyboard focus with the actual renderer. |
| 2 | An update to one task can remove keyboard focus from an unchanged task. An Ask context update can take focus from a suggestion, and the Ask window can extend outside a narrow display. | Keep unchanged task groups attached, preserve keyboard focus, and keep Ask within the work area at larger text sizes. Check keyboard operation, forced colours and a small work area. |
| 3 | A streamed link or code span can reach speech half formed. A system utterance behind a long answer can time out before it reaches the speaker. A disconnected mic can report ready after device enumeration finishes. | Preserve text boundaries, watch the playback queue head, and ignore stale capture callbacks. Exercise stream splits, held queues, Stop, device removal and late permission results. |
| 4 | A failed speech correction leaves a dead form, and Forget by list index can delete the wrong correction after a concurrent update. | Retain the editable correction on failure. Bind removal to the exact saved entry and test stale clicks and replacement entries. |
| 5 | Voice control depends on wake detection even when the user is at the keyboard. The model process can become ready before the microphone capture is ready. | Add a keyboard-accessible **Listen once** action that reports permission, model and capture readiness. Start one fresh, bounded request, reuse local audio and Voice Match, and cancel on mute, Stop, lock or device loss. Establish the temporary capture lifecycle before offering this with wake off. |
| 6 | A transcript heuristic can remove intended repetitions, and the benchmark's net error delta can hide harmful corrections. Endpoints and echo still vary by device and speaking style. | Count corrected and harmed examples independently. Benchmark legitimate repetitions, names, numbers, noise and pauses before changing recognition or endpoints. Surface uncertain input for repair where the recognizer supports a trustworthy signal. |
| 7 | Playback scheduling shows that audio was queued, and gives a coarse completion signal. It cannot account for the words someone heard before interruption. | Record local request-to-first-audio and interruption-to-silence measurements. Validate cancellation, quiet speakers, echo and unplug/replug on real devices. Add replay or a short recap through the existing conversation path once playback ownership is reliable. |
| 8 | The app has model choice and aggregate session usage but hides the conversation window reported by Copilot. SDK and extension capabilities are scattered. | Show current context separately from cumulative usage and billing, clear it on session changes, and say when the limit is unknown. Show only capabilities supported by the selected model and provider. |
| 9 | The runtime normalises dotted MCP tool names. A grant keyed by a display name alone can be ambiguous when a tool shares that runtime name. | Map raw names to the runtime name, reject ambiguous grants, and verify the originating server and tool metadata. Exercise the actual bundled runtime, description pinning, denial and revocation. |
| 10 | Upkeep of the retained memory graph blocked the main process for 1.27 s at 1,000 synthetic same-subject facts and 36.3 s at 5,000. | Reuse term sets, yield during upkeep, and discard a pass when the live graph changes or consent ends. Recheck persisted results and timer gaps. Also isolate semantic cache work from the urgent Stop path. |
| 11 | Settings and startup have synchronous system probes on Linux. Activity history reads can grow with the monthly audit file. Current footprint results omit active model and audio processes. | Measure cold and warm start, setup refresh, task and voice latency under load, and memory use with representative data on each native platform. Move or bound the measured blocking paths and publish repeatable local commands. |
| 12 | Persistent memory lacks account ownership across restart. Opposite preferences can be treated as duplicates. Project work has no durable workspace or trust boundary. | Define migration and deletion behaviour first. Test contradiction updates, account switches and interrupted writes. Build project sessions with a selected workspace, explicit authority, writer locking, reviewed changes and restart recovery. |

## Copilot capability map

The checkout uses the pinned TypeScript SDK and bundled runtime. GitHub's current docs cover more than the installed version and account policy can provide. Verify each capability against the pinned API, the bundled runtime, and the intended account or provider before offering a control. [GitHub SDK compatibility](https://docs.github.com/en/copilot/how-tos/copilot-sdk/troubleshooting/compatibility)

| Surface | Existing basis | Product work |
|---|---|---|
| Conversation | Streaming, saved conversations, models and reasoning effort, queueing, cancellation, compaction and usage. | Show current context with a clear unknown state. Explain what a reset removes. Keep account allowances and session context separate. Use steering only where the user can tell which turn or project receives it. |
| Desktop actions | Ember tools, hooks, guarded capture and separate task sessions. | Keep custom tool verification, the permission question, Stop and audit ahead of new tool classes. Session telemetry and automatic config discovery are disabled for this surface. |
| Integrations | Approved model providers and individually approved MCP tools. | Surface names, capabilities, consent, changed tool descriptions and revocation through Settings. Validate names and origins with the runtime's own metadata. |
| Project workspace | Existing desktop and project-session design notes. | Evaluate skills, agents, worktrees, local edits, shell, attachments, diffs, checkpoints, persistence and parallel work inside a selected project. Show the work plan and approval requests in the same task UI. Local project commands, network and publishing each need defined authority and recovery. |
| Cloud and shared sessions | SDK support depends on release, account and policy. | Treat cloud execution or a shared session as a separate choice with a named destination, a visible data summary and explicit retention. |

## Release evidence

For each PR, keep the regression, the affected native smoke run and the exact GitHub head together. For speech quality, report wake misses and false wakes, endpoint truncation, request-to-first-audio, quiet-after-Stop, and correction harm separately. Automated tests use synthetic audio. Hands-on acceptance covers microphones and speakers, accents and noise, Voice Match, keyboard-only work, and the platform screen readers.
