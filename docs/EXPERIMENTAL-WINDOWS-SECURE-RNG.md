# Fixed Windows secure RNG API witness

This separate experiment records the Windows API outcomes needed to investigate the source-built Node startup failure. It does not enable a coding backend, change any Node/OpenSSL source or runtime flags, or establish an OpenSSL, Node or FIPS compatibility claim. The existing official Node controls and the immutable source-built executable remain unchanged.

The authenticated Node22.23.5 artifact's latest native-only run [43836843382](https://github.com/komaladitya-08/Ember-Powered-by-Github-Copilot/actions/runs/43836843382) passed artifact/source/tool/recipe/PE staging and three of its four native cases. Its source-built ordinary host completed the fixed filesystem/timer program; its zero-capability LPAC process exited134 before producing the fixed report. A bounded classifier recognized only the public Node assertion at `src/node.cc:1266`, `ncrypto::CSPRNG(nullptr, 0)`. This identifies the failed assertion, without identifying a Windows API, provider or policy error.

The exact pinned source is Node22.23.5 commit [`60553651579ec33ca1aef9e1eedab2c3855f1f7e`](https://github.com/nodejs/node/tree/60553651579ec33ca1aef9e1eedab2c3855f1f7e), with bundled OpenSSL3.5.9. Its Windows seed implementation [rand_win.c:24–116](https://github.com/nodejs/node/blob/60553651579ec33ca1aef9e1eedab2c3855f1f7e/deps/openssl/openssl/providers/implementations/rands/seeding/rand_win.c#L24) selects BCrypt only when `_WIN32_WINNT >= 0x0600`; the authenticated compiled PE imports the legacy `CryptAcquireContextW`, `CryptGenRandom` and `CryptReleaseContext` APIs and does not import `BCryptGenRandom`. The witness does not assume a failure location within those calls.

The fixed C program makes these independent observations, without using any output as a replacement entropy source:

1. Acquire the default `PROV_RSA_FULL` context with null container/provider and `CRYPT_VERIFYCONTEXT | CRYPT_SILENT`; if acquired, request48bytes with `CryptGenRandom`, wipe the buffer and release that known-owned context once with flags0.
2. Only if the first path produced no entropy, take the same source-conditional Intel provider/type22 path from `rand_win.c:109–116`, with the same request, flags, wipe and ownership checks. This records the existing source path; it proposes no product fallback.
3. Separately call `BCryptGenRandom(NULL, buffer, 48, BCRYPT_USE_SYSTEM_PREFERRED_RNG)` and record its raw NTSTATUS, then wipe the buffer.

The48byte request is grounded in the default AES256 CTR DRBG's32byte entropy plus16byte nonce requirement: [drbg_ctr.c:543–545](https://github.com/nodejs/node/blob/60553651579ec33ca1aef9e1eedab2c3855f1f7e/deps/openssl/openssl/providers/implementations/rands/drbg_ctr.c#L543), combined when the seed source lacks a separate nonce callback by [drbg.c:405–436](https://github.com/nodejs/node/blob/60553651579ec33ca1aef9e1eedab2c3855f1f7e/deps/openssl/openssl/providers/implementations/rands/drbg.c#L405). It is a single fixed request, not a random-output quality test or a claim about every OpenSSL configuration.

Microsoft documents [default CSP selection](https://learn.microsoft.com/en-us/windows/win32/seccrypto/cryptographic-service-provider-contexts), [acquire flags/errors](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptacquirecontextw), [CryptGenRandom](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptgenrandom), [release flags](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptreleasecontext) and [system-preferred BCrypt RNG](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom). These API pages do not promise success in zero-capability LPAC. CNG success would establish one API prerequisite on the observed image, not explain an OpenSSL failure or attest FIPS mode. No registry, policy, FIPS, token, capability or ACL changes are made.

## Ownership and readout

A separate repository-source issuer, `ember-experimental-windows-secure-rng-fixed-probe`, binds the fixed C source, build recipe, selected hosted image and40hex compile commit. The builder verifies VS17/VS18 respectively, shared v14314.44.35207 and SDK10.0.26100.0; it hashes the selected compiler/linker/vcvars/vswhere before and after compilation and checks the staged x64 console PE. It produces one fixed executable. No OpenSSL/Node build, downloaded runtime or test mock belongs to this recipe.

The independently inspected ordinary-host process runs the original verified build image. The LPAC process runs its read-only LOW copy with the existing zero-capability/AAP checks, private job, exact suspended image/process checks and exactly two allowed incoming stdio handles. Host-only canary access, parent process read/duplicate/create denials, self-query, no native output, unchanged canary and complete private-job cleanup remain required. The ordinary host must demonstrate useful default-CSP and BCrypt generation. The LPAC checks require successful exit, complete controls and known cleanup independently of whether either API generated entropy.

A failed acquire with an unexpected nonzero output, a successful acquire with null output, or an uncertain release terminalizes the C child. It wipes the fixed buffer, retains any possibly owned context and waits for the parent deadline/Stop. It never retries an uncertain release or continues to another provider/API. A report-close uncertainty also waits for Stop. The parent reads no report after a root-exit deadline, missing job-zero lease or nonzero exit; child-internal uncertainty is bounded by Stop, while uncertain host ownership permanently fences further native actions and retains all owners.

The fixed192byte private report contains only role/stage/control facts, API attempt/success bits, immediate failed-BOOL error codes or raw NTSTATUS, known cleanup and wipe state. Its strict semantic parser rejects pending/uncertain ownership, incomplete releases, skipped-provider contradictions and unwiped buffers. No entropy bytes, entropy hash, seeds, statistics, provider names, private paths, process IDs, SIDs or handles are published. Numeric observations are published only after root exit, private-job zero and verified teardown.

## Verification

The separate workflow runs the unchanged ordinary-host/LPAC containment controls on Windows Server2022 and2025. Actual native results for this new witness are pending; local Linux success is not native Windows evidence.

Portable contracts test strict reports, build receipts, PE framing, the clean launch environment and terminal ownership. A separate Linux-only harness compiles the actual unchanged fixed C file with test-only API declarations and injected acquire/generation/release/CNG/report-close outcomes. It checks immediate error capture, wiping, release-once and terminal non-continuation. Those mocks generate no entropy and establish no Windows ABI, operating-system policy, LPAC or cryptographic behavior.
